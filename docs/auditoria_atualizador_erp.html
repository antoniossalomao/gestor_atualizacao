§1Resumo executivo

A avaliação anterior comparava três documentos entre si. Esta comparou os documentos com o código de verdade — o painel em web/ e o serviço Windows em Atualizador automatico/ — e a notícia principal é boa: o projeto é mais real do que qualquer um dos documentos deixa transparecer. O agente C#/.NET existe, compila, e implementa a sequência GFIX → GBAK → BScript → GBAK → injeção de BLOB → GFIX exatamente como descrita no Documento_Tecnico_Atualizador_ERP.pdf.

Mas ler o código também trocou o risco principal do projeto. A revisão anterior temia que uma heurística de "erro não estrutural" do BScript mascarasse uma atualização quebrada como sucesso. Essa heurística não existe no código — qualquer código de saída diferente de zero já aborta e tenta reverter. Um problema real e silencioso é outro: quando uma atualização falha, o campo que registra a versão-alvo nunca é desfeito, então a próxima consulta do agente já enxerga o cliente como "em dia" e para de tentar — sem jamais ter aplicado a versão. Ver achado crítico.

Uma segunda passada foi além do código: abriu o BScript.exe e o BEXE.FDB de produção reais (pasta Arquivos para analise/) por engenharia reversa de strings, e leu uma amostra dos 1026 scripts DDL históricos que o BScript aplica. O resultado mudou a prioridade da auditoria: há fortes indícios de que o BScript.exe real é uma aplicação gráfica interativa, sem nenhum modo de linha de comando — o que tornaria o passo mais crítico da Fase 3 (chamá-lo "de forma silenciosa" via Process.Start) capaz de travar o servidor inteiro do cliente, não apenas de falhar silenciosamente. Ver achado crítico.

Nove dos onze achados já foram corrigidos diretamente no código do agente (Atualizador automatico/), com dotnet build validado sem erros: a reversão de versão em falha, o schema real do BEXE.fdb, a transação única na injeção de binários, o backoff após erro, o uso do campo script_url, a porta configurável do Firebird, a gravação de MENSAGEM_LOG, os argumentos de processo via ArgumentList, e a extração por lista explícita de arquivos. Os dois que restam não são corrigíveis só com código: o risco do BScript.exe ganhou uma rede de segurança (timeout que mata o processo) mas continua exigindo confirmação com quem mantém o binário real, e a estratégia de quais dos 1026 scripts cada versão exige é uma decisão de processo, não uma linha de código.

§4Achados novos, visíveis só no código

Nenhum dos três documentos tem como revelar estes pontos — eles vivem em decisões de implementação que só aparecem lendo o C# e o Node.js linha a linha, ou, nos quatro primeiros casos abaixo, abrindo os próprios binários e a base de produção.

Contra os binários e a base reais (Arquivos para analise/)

Crítico

O BScript.exe real parece ser um programa gráfico interativo — sem evidência de nenhum modo silencioso

Extraindo as strings do binário real (5 MB, compilado em 2019) aparece um formulário Delphi/FireDAC completo: campos de texto para Servidor, Banco e pasta de Scripts; um seletor de arquivos .sql/.fdb com multisseleção manual (TFileOpenDialog); um RadioGroup para filtrar resultados ("Critical Erro", "Erro - Ok", "Ok", "Todos"); e dois botões — "Selecionar Scripts Pasta" e "Inserir No Banco Como Executado" — este último claramente uma confirmação manual, feita depois de olhar o resultado na tela.

Em nenhum lugar dos 5 MB do binário aparece uma string reconhecível de parsing de linha de comando: nenhuma ocorrência de /silent, -silent, FindCmdLineSwitch, -db= ou equivalente. A única ocorrência de "ParamCount" encontrada pertence à RTTI interna do compilador Delphi (TVmtMethodEntryTail.ParamCount), não a leitura de argumentos do programa.

Onde
Arquivos para analise/BScript.exe (strings nos offsets ~5.08M e ~2.55M) · assumido em Worker.cs:79
Cenário
Worker.cs chama BScript.exe /silent /db="..." como se fosse um executável de linha de comando. Rodando dentro de um Windows Service (sessão 0, sem desktop interativo), o mais provável é uma janela que ninguém consegue ver nem clicar — e Process.WaitForExitAsync() no C# fica esperando indefinidamente, com o banco ainda em gfix -shut force_0 (bloqueado para todo mundo) até alguém notar e matar o processo manualmente no servidor do cliente.
Correção
Confirmar com quem mantém o BScript.exe se existe uma versão/branch com modo linha de comando de verdade. Se não existir, ele precisa ganhar um modo headless (ou ser substituído por um executor de scripts escrito para isso) antes de qualquer piloto — não há como automatizar com segurança em cima da versão atual.
Status
Mitigado, não resolvido — ProcessService.RunProcessAsync agora exige timeout e mata o processo se estourar (ProcessService.cs), então uma trava não bloqueia o servidor para sempre. Mas isso é uma rede de segurança, não uma confirmação de que a automação funciona — a decisão sobre o BScript real continua pendente.
Alto

O schema real do BEXE.fdb usa nomes diferentes dos que o agente assume

Abrindo o BEXE.FDB real de produção (44 MB) e extraindo os identificadores gravados nas páginas de metadados do Firebird, a única tabela de aplicação encontrada é EXECUTAVEIS, com os campos NOMEPRODUTO, NOMEARQUIVO, VERSAO, VERSAOATUALIZADA, EXECUTAVEL, HASHEXE e DATA_ATUALIZACAO. O código do agente assume uma tabela VERSOES_EXE com colunas NOME_EXE e ARQUIVO_BLOB — nomes que não existem neste banco. Contra o arquivo real, InjetarNovosBinarios falharia já na primeira execução.

De bônus: o schema real já reserva um campo HASHEXE — provavelmente usado pelos terminais para validar o executável antes de rodar. O código atual não escreve nada nele; mesmo depois de corrigir o nome da tabela, esse campo ficaria nulo.

Onde
DatabaseService.cs:62-64 (nomes assumidos, com comentário admitindo o chute) vs. Arquivos para analise/BEXE.FDB (schema real, confirmado por engenharia reversa)
Correção
Reescrever InjetarNovosBinarios contra o schema real (EXECUTAVEIS / NOMEARQUIVO / EXECUTAVEL / HASHEXE) e decidir o que gravar em HASHEXE — o SHA-256 já calculado no download é o candidato natural.
Status
Corrigido — DatabaseService.cs agora grava em EXECUTAVEIS com os nomes reais de coluna e popula HASHEXE com o SHA-256 do arquivo. NOMEPRODUTO usa o nome do arquivo sem extensão como padrão; confirmar se é essa a convenção esperada pelos terminais.
Médio

O BScript.Ini real, em uso hoje, aponta Server=localhost/3051 — uma porta não padrão. O agente C# grava Port=3050 fixo na connection string, sem variável de ambiente para ajustar. Num cliente cujo Firebird escute em 3051 (como este próprio arquivo de configuração real evidencia que acontece), o agente simplesmente não conseguiria abrir conexão nenhuma com o JUNIOR.fdb.

Onde
DatabaseService.cs:12 vs. Arquivos para analise/BScript.Ini:2
Correção
Expor a porta como variável de ambiente (ex.: ATUALIZADOR_DB_PORT), com 3050 como padrão.
Status
Corrigido — DatabaseService.cs lê ATUALIZADOR_DB_PORT, com 3050 como padrão.
Baixo

1026 scripts DDL reais, nenhum protegido contra reexecução — e "já aplicado" hoje é um clique manual

Amostrando os scripts em Scripts-BVendas/ (1026 arquivos, de 2011 até 12/08/2026) — por exemplo ALTER TABLE PRODUTOS ADD LABORATORIO VARCHAR(40); e create table garantia_remessa(...) — nenhum tem checagem de existência prévia (nem IF NOT EXISTS, nem EXECUTE BLOCK consultando RDB$RELATION_FIELDS). No próprio BScript.exe, o botão "Inserir No Banco Como Executado" é uma ação manual, separada da execução em si — sugerindo que, hoje, marcar um script como "já aplicado" é decisão humana, não efeito automático do sucesso da migração.

Isso dá corpo ao risco de idempotência já levantado antes: sem uma marcação automática, rodar os scripts sem saber quais já foram aplicados naquele cliente específico gera erros "objeto já existe" em qualquer cliente que não parta de um banco zerado — exatamente os erros que a política atual do agente (qualquer código de saída ≠ 0 aborta e reverte) trataria como falha crítica do zero ao cem.

Onde
Scripts-BVendas/*.sql (amostra) · fluxo de dois botões do BScript.exe · ProcessService.cs:35-36
Correção
O BScript precisa de uma tabela de controle que ele mesmo consulte antes de tentar cada script (pulando os já aplicados automaticamente), ou o agente precisa receber uma lista explícita "quais scripts esta versão exige" em vez de apontar para a pasta inteira de scripts históricos.
Status
Em aberto — é uma decisão de processo (não só de código): como versionar quais scripts cada release exige. Nenhuma mudança de código resolve isso sozinha.

Do código do painel e do agente

Crítico

Uma atualização que falha some do radar em vez de ficar pendente

Assim que o agente decide baixar uma versão, ele já grava essa versão-alvo no campo VERSAO_NOVA — antes de qualquer autorização ou execução. Se a Fase 3 falhar e o estado virar ERRO, esse campo não é revertido. Na próxima vez que o agente perguntar "há algo mais novo que VERSAO_NOVA?", a resposta da API é não, porque o valor enviado já é igual ao publicado. O cliente fica permanentemente na versão antiga, mas tanto o agente quanto o painel param de sinalizar pendência — o único rastro é um log de erro antigo na aba Distribuição, que ninguém é obrigado a olhar de novo.

Isso reproduz exatamente o perigo que a revisão anterior atribuía a uma "heurística de erro não estrutural" do BScript — só que essa heurística não existe no código; o mecanismo real é este campo de versão nunca sendo desfeito.

Onde
Worker.cs:50 grava o alvo cedo demais · Worker.cs:105 não reverte no catch · DatabaseService.cs:24-31 lê o mesmo campo como "versão atual" · VersaoService.js:68-72 compara os dois
Cenário
BScript falha por disco cheio → estado ERRO, mas VERSAO_NOVA já é "2026.08.10" → próximo polling não detecta pendência → cliente nunca mais recebe a versão, sem alarme ativo.
Correção
Separar "versão instalada confirmada" de "versão-alvo em andamento", ou reverter VERSAO_NOVA ao valor anterior dentro do bloco catch de Worker.cs.
Status
Corrigido — a versão anterior é salva num arquivo local antes da Fase 1 sobrescrever o campo, e restaurada no catch de ProcessarAtualizacao junto com a mensagem de erro em MENSAGEM_LOG.
Alto

Injeção de BLOB no BEXE não é transacional nem revertida em falha

Cada executável é gravado no BEXE.fdb num UPDATE/INSERT isolado, sem transação explícita envolvendo o lote inteiro. Se o terceiro de cinco arquivos falhar, os dois primeiros já foram commitados. Pior: o bloco de rollback do Worker só sabe restaurar o JUNIOR.fdb a partir do backup — ele nunca toca o BEXE.fdb. Uma falha no meio da Fase 4 deixa terminais lendo uma mistura permanente de binários antigos e novos, exatamente o Risco 3 já identificado — agora localizado e confirmado.

Onde
DatabaseService.cs:49-82 (InjetarNovosBinarios)
Cenário
Cinco EXEs, o quarto falha por lock do arquivo → três novos e dois antigos ficam em produção até a próxima tentativa bem-sucedida — se ela vier.
Correção
Envolver o laço numa única FbTransaction com commit ao final; incluir o BEXE no plano de rollback ou, no mínimo, alertar quando a Fase 4 falha parcialmente.
Status
Corrigido — todos os arquivos agora entram numa única FbTransaction, com commit só ao final e rollback automático se qualquer arquivo falhar.
Alto

O painel aceita e devolve scriptUrl no contrato de versão, e o documento técnico descreve o BScript.exe como algo distribuído pela nuvem. Só que a classe de resposta do agente (UpdateResponse) não tem propriedade para esse campo, e o Worker sempre chama um caminho fixo (ATUALIZADOR_BSCRIPT_PATH) já presente no servidor do cliente. Ou seja: atualizar a lógica do próprio BScript ainda exige cópia manual em cada servidor — a promessa de "zero toque" não cobre o script mais crítico de todos.

Corrigido — UpdateResponse agora tem ScriptUrl; se presente, o agente baixa o arquivo na Fase 1 (ApiService.DownloadFileAsync) e usa esse caminho na Fase 3 em vez do fixo.

§7Pendências que os próprios documentos já assumem — e continuam abertas

O documento técnico v1.0 lista quatro pontos em sua própria seção 11. A segunda passada desta auditoria, contra os arquivos reais em Arquivos para analise/, resolveu e corrigiu um deles no código, e piorou a leitura de outro (que agora tem uma mitigação de segurança, mas não uma confirmação) — os dois primeiros itens abaixo foram atualizados; os dois últimos seguem exatamente como o documento técnico já assumia, fora do alcance de uma correção de código.

  • Schema do BEXE.fdb — resolvido e corrigido. A tabela real é EXECUTAVEIS (colunas NOMEPRODUTO, NOMEARQUIVO, VERSAO, VERSAOATUALIZADA, EXECUTAVEL, HASHEXE, DATA_ATUALIZACAO), confirmada abrindo o BEXE.FDB real, e DatabaseService.cs já foi reescrito para usá-la. O schema do JUNIOR.fdb (a tabela SYS_ATUALIZACAO em si) continua não confirmado; nenhuma cópia desse banco estava disponível para inspeção.
  • Comando silencioso real do BScript — mitigado, não resolvido. A engenharia reversa do binário real não encontrou nenhuma evidência de que ele aceite argumentos de linha de comando, e encontrou fortes evidências de que é puramente interativo (formulário, seletor de arquivo, botão de confirmação manual). O código ganhou um timeout de segurança que mata o processo se ele travar (ver achado crítico em §4) — isso evita o pior cenário (servidor bloqueado para sempre), mas não substitui confirmar com quem mantém o binário se existe mesmo um modo automatizável.
  • Procedimento de restauração — o comando gbak -c -replace_database existe no código de rollback, mas nunca foi exercitado contra uma cópia real do Firebird 2.5 do cliente.
  • Integração Delphi — não há qualquer arquivo .pas/.dpr no repositório; a Fase 2 inteira (ler PENDENTE, perguntar, gravar AUTORIZADO) ainda precisa ser escrita no ERP real.

§8Prioridades antes de um piloto
