Atualizador Inteligente de ERP

Documento técnico e executivo sobre a automação de versões, agentes locais, integração com Delphi e segurança dos dados.

Versão do documento: 1.0
Data: 26 de agosto de 2026

1. Visão geral

O Atualizador Inteligente de ERP é um ecossistema para reduzir a intervenção manual no processo de atualização dos clientes. A solução combina um painel web central, um agente local executado no servidor do cliente e a participação do ERP Delphi na decisão do momento da atualização.

O objetivo não é apenas copiar novos executáveis. Uma atualização pode alterar o banco de dados, executar scripts, substituir componentes e afetar vários terminais. Por isso, o processo precisa ser preparado, autorizado, executado e registrado de forma previsível.

Objetivo principal: detectar novas versões, baixar pacotes silenciosamente, pedir autorização ao usuário e executar backups, scripts e distribuição com controle sobre o Firebird 2.5.

2. O problema atual

O processo tradicional depende de intervenção da equipe de suporte em cada cliente. Essa dependência consome tempo, dificulta a padronização e aumenta a possibilidade de erro humano.

  • O suporte precisa acompanhar cada atualização manualmente.
  • Existe o risco de esquecer o backup antes de aplicar alterações de banco.
  • O cliente pode ser interrompido durante uma operação comercial.
  • Pacotes de formatos diferentes exigem tratamento operacional adicional.
  • É difícil saber rapidamente quais clientes foram atualizados, quais falharam e em que etapa.

4. Componentes implementados

4.1 Painel web

O painel web é acessado pelo navegador e permite que a equipe trabalhe com uma base compartilhada. Ele possui login multiusuário, resumo operacional, cadastro de clientes, atualizações, agenda, consulta, sistemas, histórico, backups e distribuição de versões.

  • Resumo com indicadores de clientes e atualizações.
  • Cadastro e consulta de clientes.
  • Registro, busca, filtros e importação/exportação de atualizações.
  • Agenda de tarefas e lembretes.
  • Histórico das ações realizadas pelos usuários.
  • Cadastro e publicação de versões.
  • Retorno dos agentes por cliente e status.

4.2 API central

A API organiza as regras de negócio em rotas, controllers, serviços e repositórios. O banco SQLite é acessado por uma camada própria de persistência. Backups automáticos do banco são realizados quando o servidor é iniciado.

4.3 Agente local

O agente é um serviço Windows baseado em .NET 8. Ele executa em segundo plano, consulta a API em intervalos regulares e realiza o trabalho pesado sem exigir que o usuário permaneça acompanhando cada etapa.

5. Ciclo completo da atualização

Fase 1 - Preparo invisível

  1. O agente consulta a API usando o CNPJ do cliente, a versão atual e o token do agente.
  2. A API informa se existe versão publicada superior.
  3. O agente baixa os pacotes correspondentes.
  4. O SHA-256 do download é conferido antes da utilização.
  5. O 7za.exe extrai pacotes .7z, .rar e .zip.
  6. Os arquivos executáveis e scripts ficam em uma pasta temporária.
  7. O agente grava PENDENTE em SYS_ATUALIZACAO no JUNIOR.fdb.

Fase 2 - Decisão do usuário

Ao abrir o ERP, o Delphi consulta a tabela de controle. Quando encontra o estado PENDENTE, apresenta uma mensagem informando que existe uma nova versão pronta e que o sistema precisará ser reiniciado.

  • Se o usuário confirmar, o ERP grava AUTORIZADO e encerra-se.
  • Se o usuário não confirmar, a operação continua normalmente e a atualização permanece aguardando.

Fase 3 - Execução segura

  1. O agente marca o estado como PROCESSANDO.
  2. Executa gfix -shut force_0 para isolar o banco.
  3. Executa o primeiro gbak, criando o backup pré-atualização.
  4. Executa o BScript.exe de forma silenciosa.
  5. Executa o segundo gbak, registrando o banco após a alteração.

Fase 4 - Distribuição limpa

  1. O agente localiza os executáveis extraídos.
  2. Conecta ao BEXE.fdb.
  3. Converte os executáveis em dados binários e grava os BLOBs de distribuição.
  4. Executa gfix -online no banco principal.
  5. Os terminais leem o BEXE.fdb e realizam sua atualização.
  6. O estado final é gravado como CONCLUIDO e o resultado é enviado à API.

7. Segurança e recuperação

  • Endpoints do agente usam token próprio no header X-Agent-Token.
  • O painel web usa sessão com cookie HttpOnly e limite de tentativas de login.
  • Downloads validam o nome do arquivo e o SHA-256.
  • Credenciais do Firebird devem ser fornecidas por configuração protegida, nunca gravadas no código.
  • Os argumentos dos processos não são registrados nos logs para evitar exposição de senha.
  • O banco é isolado antes de alterações estruturais.
  • O backup pré-atualização é preservado para tentativa de restauração em caso de falha.
  • O agente mantém o banco online mesmo quando uma etapa falha, registrando o estado de erro.
Importante: a automação não substitui o teste de restauração. O rollback precisa ser validado com uma cópia descartável e com a versão real do Firebird instalada no cliente.

8. Formatos de pacotes

O agente utiliza o motor 7za.exe para lidar com pacotes novos e legados. Essa decisão evita criar um extrator diferente para cada extensão e permite que a equipe mantenha um fluxo único para .7z, .rar e .zip.

Após o download, o pacote é validado por SHA-256, extraído em diretório temporário e só então disponibilizado para a execução. A ausência do extrator interrompe o ciclo para impedir que uma atualização seja marcada como pronta sem seus arquivos.

10. Implantação

  1. Definir SESSION_SECRET, AGENT_API_TOKEN e PUBLIC_URL no servidor.
  2. Configurar no agente a URL da API, token, CNPJ, caminhos dos bancos, credencial Firebird e caminhos do GFIX, GBAK e BScript.
  3. Colocar o 7za.exe ao lado do executável publicado.
  4. Publicar e instalar o agente como serviço Windows.
  5. Testar permissões de leitura e escrita nos bancos.
  6. Executar um ciclo completo em ambiente de testes.
  7. Realizar piloto controlado antes da distribuição geral.

Para uso pela internet, recomenda-se proxy reverso com HTTPS e SESSION_SECURE=true. Para uso apenas na rede local, o servidor pode ser acessado pelo IP da máquina que hospeda o backend.

12. Conclusão

A arquitetura proposta separa claramente o que acontece na nuvem, no servidor do cliente e dentro do ERP. O painel centraliza controle e rastreabilidade; o agente local executa operações técnicas; e o Delphi mantém a experiência e a decisão do usuário.

O projeto já possui a base necessária para um piloto. A entrada em produção deve acontecer somente depois da validação dos schemas reais, da integração Delphi, do comando do BScript e do procedimento de restauração do Firebird.
